## 1. Общие сведения

### 1.1 Наименование и обозначение ПО

- **Полное наименование:** «Health-Bot-AI — интеллектуальный ассистент отдела
  продаж OCX для консультирования по продуктам здоровья и бережного очищения
  организма».
- **Условное обозначение:** Health-Bot-AI / HBAI.
- **Тип ПО:** веб-приложение и REST API.
- **Версия:** 1.0.
- **Язык интерфейса:** русский.
- **Язык кода и технической документации:** русский с английскими терминами.

### 1.2 Юридические аспекты для передачи прав

Проект демонстрационный; реальные реквизиты и договоры не используются. При
передаче прав в промышленную эксплуатацию оформляются:

- договор на разработку ПО / договор авторского заказа;
- лицензионный договор о передаче исключительных прав;
- акт приёма-передачи прав и результатов работ;
- NDA;
- поручение на обработку ПДн по ч. 3 ст. 6 152-ФЗ;
- согласие пилотных пользователей на обработку ПДн;
- реестр open-source-компонентов и их лицензий;
- соглашение об уровне поддержки (SLA).

Ключевые условия:

- исключительные права на собственный код и документацию передаются Заказчику
  после полной оплаты и подписания акта;
- open-source-компоненты используются по их лицензиям; GPL/AGPL в проприетарном
  контуре допускаются только по отдельному согласованию;
- ПДн пользователей хранятся и обрабатываются на территории РФ;
- перечень субпроцессоров (AITunnel, Yandex Cloud и др.) фиксируется отдельно;
- передача ПДн за пределы РФ допускается только при наличии законного основания
  и после отдельной юридической оценки;
- товарный знак OCX, контент базы знаний и промпты являются охраняемыми объектами.

> AITunnel может маршрутизировать запросы к зарубежным моделям. Для
> промышленного контура предпочтительны LLM, размещённые в РФ; иное требует
> юридической оценки и, при необходимости, согласия субъектов ПДн.

## 2. Цели и назначение ПО

### 2.1 Назначение

Health-Bot-AI — B2B-сервис для менеджеров отдела продаж OCX. На входе:
контекст сделки из CRM и сообщение клиента. На выходе:

1. готовый ответ клиенту;
2. внутренняя подсказка менеджеру по допродаже;
3. признак необходимости допродажи;
4. ссылки на источники из базы знаний;
5. флаги безопасности.

Система **не является медицинским изделием**, не ставит диагнозы и не заменяет
врача. Все ответы носят информационно-справочный характер.

### 2.2 Цели и KPI

| Цель | Целевой показатель |
|---|---|
| Сократить время подготовки ответа | с 5–10 минут до ≤ 1 минуты |
| Повысить средний чек | +10% к базовому уровню |
| Повысить конверсию в допродажу | +10% relative |
| Стандартизировать качество ответов | ≥ 90% корректных на golden set |
| Снизить риск утечки ПДн | 0 инцидентов |
| Обеспечить масштабирование | 1000 одновременных запросов в R1 |
| Удовлетворённость менеджеров | CSAT ≥ 4,5 / 5 |
| Автоматизация типовых вопросов | ≥ 70% |

#### 3.1.1 FR-01. Ввод и валидация обращения

- **P0, MVP.**
- UI: поля «Контекст сделки», «Сообщение клиента», выбор провайдера, варианта
  промпта, streaming, temperature, max tokens.
- Валидация: непустые значения после `trim`, длина до 4000 символов, UTF-8,
  экранирование HTML.
- API: JSON-схема, коды 422 с указанием полей, ограничение размера тела запроса.
- Ошибки показываются пользователю без потери введённых данных.
- **Приёмка:** пустая строка/пробелы → 422; 4001 символ → 422; корректный
  запрос → 200; в логах нет сырых ПДн.

#### 3.1.2 FR-02. Анонимизация ПДн

- **P0, MVP.**
- До любого внешнего вызова маскируются оба поля и история диалога.
- Типы ПДн: ФИО, телефоны, e-mail, адреса, СНИЛС, ИНН, паспорт, дата рождения,
  банковская карта, расчётный счёт, IP-адрес.
- Используются согласованные плейсхолдеры в рамках запроса: `[КЛИЕНТ_1]`,
  `[ТЕЛЕФОН_1]` и т.п.
- Соответствие «плейсхолдер → исходное значение» хранится только в оперативной
  памяти и никогда не пишется в логи, БД, кэш и трассировки.
- Базовая реализация: regex-распознаватели + расширяемый реестр; Presidio/spaCy
  подключаются как дополнительный слой при наличии зависимостей.
- **Приёмка:** golden set из 100 примеров — 0 утечек; ложноположительные
  срабатывания ≤ 5%; сырые ПДн отсутствуют в исходящем запросе и `audit.log`.

#### 3.1.3 FR-03. Генерация ответа клиенту

- **P0, MVP.**
- Ответ строится только на базе знаний; при наличии RAG — со ссылками на источник.
- Объём: 3–5 предложений; русский язык; тон зависит от выбранного варианта
  промпта.
- Запрещено: ставить диагноз, назначать лечение, гарантировать результат,
  использовать формулировки «лечит», «безопасно для всех».
- Обязательный дисклеймер: «Не является медицинской рекомендацией».
- Red flags (беременность, хронические заболевания, приём лекарств, острые
  симптомы) → рекомендация обратиться к врачу и эскалация менеджеру.
- Цены, скидки и доставка считаются детерминированным калькулятором/инструментом,
  а не «в уме» LLM.
- Если данных в БЗ нет — честный ответ «нет информации» и предложение уточнить
  у менеджера.
- **Приёмка:** ≥ 95% ответов подтверждены БЗ; 0 запрещённых медицинских
  утверждений на тестовом наборе.

#### 3.1.4 FR-04. Подсказка менеджеру по допродаже

- **P0, MVP.**
- Содержит: продукт, акцию, цену, следующий шаг, отработку возражения,
  ожидаемую сумму чека.
- Признак `needs_upsell`; если допродажа не нужна — строка
  «Допродажа не требуется».
- Подсказка является отдельным полем и **никогда** не попадает в ответ клиенту.
- Учитываются: текущая сумма заказа, доставка, акция «Витамин-Буст −20%»,
  порог бесплатной доставки 5000 ₽.
- **Приёмка:** для сценария «Детокс 4500 ₽» подсказка предлагает
  «Витамин-Буст» за 1680 ₽ и итог 6180 ₽; внутренний текст не виден клиенту.

#### 3.1.5 FR-05. Контракт ответа и парсинг

- **P0, MVP.**
- Предпочтительный формат — JSON: `client_answer`, `manager_tip`,
  `needs_upsell`, `citations`, `confidence`, `safety_flags`, `provider`, `model`,
  `usage`, `request_id`, `cache_hit`.
- Парсер устойчив к markdown-обёрткам и старым двум блокам
  `=== БЛОК ДЛЯ КЛИЕНТА ===`.
- При невалидном ответе — безопасный fallback, запись инцидента, retry.
- Chain-of-thought и системный промпт не возвращаются пользователю.
- **Приёмка:** ≥ 99% валидных ответов на golden set; malformed-ответ не приводит
  к 500.

#### 3.1.6 FR-06. Провайдеры, fallback и streaming

- **P0, MVP.**
- Основной провайдер — AITunnel; резервный — YandexGPT.
- В MVP активен один провайдер; в R1 — цепочка с fallback.
- Таймауты, retry с backoff и jitter, circuit breaker, ограничение параллельных
  запросов на провайдера.
- Streaming: первый токен ≤ 3 с; fallback допускается **только до первого
  токена**; после первого токена — ошибка без смешивания ответов.
- Выбор провайдера и модели — через конфигурацию/админку.
- **Приёмка:** отключение основного провайдера → ответ резервного; смешанных
  ответов нет; 429/5xx обрабатываются.

#### 3.1.7 FR-07. База знаний и RAG

- **P1, R1.**
- БЗ версионируется; загрузка Markdown/PDF/DOCX; чанки 500–800 токенов;
  эмбеддинги; хранение в PostgreSQL + pgvector.
- Поиск top-k с фильтрами по продукту/акции; цитаты в ответе.
- Админ: черновик → проверка → публикация → откат версии; аудит изменений.
- В MVP допускается передача всей БЗ, если она ≤ 8k токенов; в R1 — только RAG.
- **Приёмка:** публикация БЗ применяется ≤ 5 минут; откат версии работает;
  ответ содержит источник.

#### 3.1.8 FR-08. Кэширование ответов

- **P0, MVP.**
- Хранилище — Redis; TTL 24 часа; максимальный размер задаётся конфигом.
- Ключ: SHA-256 от анонимизированного ввода + версия промпта + версия БЗ +
  провайдер + модель + temperature + max_tokens.
- Инвалидация при публикации БЗ/промпта; защита от cache stampede.
- В кэше нет ПДн; метрики hit ratio.
- **Приёмка:** cache hit p95 ≤ 300 мс; после публикации новой БЗ старые ответы
  не отдаются; несколько воркеров видят общий кэш.

#### 3.1.9 FR-09. История и память диалога

- **P1, R1.**
- История последних 10 обращений в сессии; multi-turn — последние N сообщений
  или суммаризация.
- TTL истории; кнопка «Очистить».
- Сырые ПДн не сохраняются; только анонимизированный текст.
- **Приёмка:** контекст сохраняется между запросами; очистка удаляет историю;
  в БД нет сырых ПДн.

#### 3.1.10 FR-10. Webhook API и интеграция с CRM

- **P0, MVP — webhook; R1 — AmoCRM.**
- REST/JSON, OpenAPI 3.1, версия `/v1`.
- Эндпоинты: `POST /v1/consult`, `POST /v1/consult/stream` (SSE),
  `POST /v1/feedback`, `GET /health`, `GET /ready`.
- Аутентификация: API key или OAuth2 client credentials; HMAC-подпись входящих
  webhook.
- Rate limit, idempotency key, `request_id`, таймауты, коды 4xx/5xx без stack
  trace.
- AmoCRM: OAuth2, проверка подписи, работа с полями сделки/контакта, заметками
  и чатом; retry и дедупликация.
- Поля `prompt_variant` и `use_cache` обязательны к исполнению.
- **Приёмка:** contract-тесты; 401/429; повтор с тем же idempotency key не
  создаёт дубль; подпись проверяется.

#### 3.1.11 FR-11. Роли и доступ

- **P1, R1.**
- Роли: менеджер, администратор, аудитор.
- RBAC; SSO/OIDC — опционально; таймаут сессии; MFA для администраторов.
- Все действия с БЗ, промптами и пользователями — в аудите.
- **Приёмка:** менеджер не имеет доступа к админке; аудитор видит журнал,
  но не меняет данные.

#### 3.1.12 FR-12. Аудит и соответствие 152-ФЗ

- **P0, MVP — аудит; R1 — БД и retention.**
- События: кто, когда, `request_id`, действие, провайдер, модель, latency,
  токены, cache hit, успех, количество ПДн по категориям (без значений).
- Неизменяемое хранение; срок хранения — по закону и политике Заказчика
  (ориентир — 1 год); экспорт и удаление по запросу.
- Запрещено писать сырые ПДн в логи, метрики и трассировки.
- DPIA, согласия, уведомление РКН, план реагирования на инциденты.
- **Приёмка:** аудит-запрос по `request_id`; удаление по субъекту; проверка
  отсутствия ПДн в логах.

#### 3.1.13 FR-13. Обратная связь и качество

- **P1, R1.**
- Оценка менеджером 1–5, причина, флаг «корректно/некорректно».
- Хранение оценки, dashboard, golden set, A/B-сравнение промптов и моделей.
- **Приёмка:** оценка сохраняется; отчёт строится; A/B показывает метрики.

#### 3.1.14 FR-14. Администрирование и мониторинг

- **P1, R1.**
- Админка: БЗ, промпты, провайдеры, лимиты, пользователи.
- Health/readiness, метрики, алерты, стоимость токенов, просмотр логов.
- **Приёмка:** администратор может опубликовать БЗ и откатить версию;
  алерт при недоступности провайдера.

#### 3.1.15 FR-15. Безопасность и guardrails

- **P0, MVP.**
- Детекция prompt injection; защита системного промпта; модерация входа/выхода.
- Медицинские guardrails: red flags, запрещённые утверждения, дисклеймер,
  эскалация человеку.
- Контроль утечки ПДн; rate limit; WAF; секреты вне репозитория.
- **Приёмка:** red-team набор из 50 атак — 0 критичных обходов; запрещённые
  формулировки блокируются.

#### 3.1.16 FR-16. UI/UX

- **P0, MVP.**
- Streamlit-интерфейс: адаптивность, копирование ответа и подсказки, очистка
  формы, история, streaming, понятные ошибки, техническая информация.
- Доступность WCAG 2.1 AA; мобильная версия; ≤ 3 клика до результата.
- **Приёмка:** нет дублирования блоков ответа и сайдбара; все сценарии проходят
  UAT.

### 3.2 Нефункциональные требования

#### 3.2.1 Надёжность

- Доступность: 99,5% для MVP, 99,9% для R1.
- RTO ≤ 1 час, RPO ≤ 15 минут для БД.
- Graceful degradation: при недоступности LLM — fallback; при недоступности
  Redis — работа без кэша; при недоступности БД — режим только чтения/очередь.
- Резервное копирование ежедневно, хранение 30 дней, проверка восстановления
  ежемесячно.
- Circuit breaker, таймауты, идемпотентность, повторные попытки.

#### 3.2.2 Масштабируемость

- Приложение stateless; горизонтальное масштабирование; общие Redis и
  PostgreSQL; без sticky sessions.
- MVP: 100 одновременных запросов; R1: 1000 одновременных, 50 RPS.
- Балансировка: Nginx/HAProxy; очередь для длительных задач; autoscaling.
- Нагрузочное тестирование перед пилотом.

#### 3.2.3 Производительность

- Накладные расходы API: p95 ≤ 200 мс.
- Кэшированный ответ: p95 ≤ 300 мс.
- Первый токен LLM: p95 ≤ 3 с.
- Полный ответ LLM: p95 ≤ 8 с, максимум 15 с.
- При 1000 одновременных запросов деградация — не более 20%.

> Требование «≤ 2 секунд при 1000 запросов» из шаблона реалистично только для
> кэшированных/детерминированных ответов. Для LLM-генерации фиксируем отдельные
> SLO выше; иначе потребуется собственный GPU-инференс.

#### 3.2.4 Показатели назначения

- Уровень автоматизации: ≥ 70% типовых обращений без правок менеджера.
- Темы: продукты, состав, цена, акции, доставка, оплата, возвраты,
  противопоказания, порядок приёма.
- Объём: до 10 000 запросов/сутки в R1.
- Точность: ≥ 90% на golden set.
- Конверсия в допродажу: ≥ 15%.
- CSAT: ≥ 4,5/5.

#### 3.2.5 Показатели качества

- Точность ответов, время отклика, CSAT, стабильность.
- Галлюцинации: ≤ 2%.
- Соответствие формату: ≥ 99%.
- Утечки ПДн: 0.
- Доля ответов с корректной ссылкой на БЗ: ≥ 95%.

- Браузеры: Chrome, Edge, Firefox, Safari — последние 2 версии.

#### 3.2.7 Требования к аппаратному обеспечению

- Python 3.12, промпты на русском, медицинский глоссарий.

## 6. Порядок контроля и приёмки

Приёмка проводится по трём контурам:

1. **Функциональный:** матрица FR-01…FR-16, все P0 — пройдены; P1 — по
   согласованию.
2. **Нефункциональный:** нагрузочный тест (100/1000 конкурирующих), failover,
   восстановление из бэкапа, security-сканирование, пентест.
3. **Комплаенс:** 0 утечек ПДн, DPIA, аудит, документы, согласия.

Критерии:

- 0 критичных и высоких дефектов; средних — не более 5 с планом устранения;
- все сценарии UAT пройдены;
- документация полная и актуальная;
- демонстрация на реальных/обезличенных данных;
- подписан акт ввода в эксплуатацию.

**Definition of Done для релиза:**

- тесты, lint, typecheck — зелёные;
- README и CHANGELOG актуальны;
- `.env`, `audit.log`, `venv`, `__pycache__` не попадают в git;
- выполнен финальный коммит и push;
- проставлен тег версии.

## 9. Финальный release-gate

В `.rules` уже есть директива о финальном коммите и обновлении README.
Дополнительно фиксируется:

1. Перед коммитом:
   - `python -m pytest -q` — все тесты зелёные;
   - `ruff check .`, `mypy src config app.py` — без ошибок;
   - README и CHANGELOG обновлены;
   - `.env`, `audit.log`, `venv`, `__pycache__`, `.pytest_cache` не в индексе;
   - PDF-шаблон находится в `docs/requirements/`;
   - в диффе нет секретов и сырых ПДн.
2. Коммит и пуш:
   ```powershell
   git status
   git add .
   git commit -m "feat: complete Health-Bot-AI production MVP and update docs"
   git push origin master
   git tag v1.0.0
   git push origin v1.0.0
   ```
3. Если push отклонён — `git pull --rebase`, повторные тесты, повторный push.
   Force-push в `master` запрещён.
